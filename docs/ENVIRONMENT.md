# Environment variables

Complete reference for every environment variable the app reads. The
short list of "you almost certainly need this in production" vars lives
in `replit.md`; this file is the full catalog.

## Core

- `APP_ENVIRONMENT`: Set to `local` or `development` to enable `/api/auth/dev-login` **and** the four fixed-password demo role accounts (`MementoAdminRole`, `AdminRole`, `LimitedAdminRole`, `UserRole` — all `Temporary1!`). Any other value, or leaving it unset, is treated as a deployed environment: those accounts are never created, so the repository-known password cannot reach production. Fails safe — a missing value means "not development".
- `BOOTSTRAP_ADMIN_PASSWORD` (optional, deployed environments only): Initial password for a single bootstrap `admin` account, so a freshly-provisioned database can be administered at all. Minimum 12 characters. The account is created **only** when the database has no `admin` or `memento_admin` user yet, is never given the god-mode `memento_admin` role, and is created with an incomplete profile so the post-login profile-completion flow prompts the operator immediately. Sign in, change the password, then unset this variable. When unset (the normal steady state) no seeding happens at all.
- `BOOTSTRAP_ADMIN_USERNAME` (optional, default `admin`): Username for the `BOOTSTRAP_ADMIN_PASSWORD` account. Set this if `admin` is already taken.
- `PROJECT_SECRETS_KEY`: Symmetric key used to encrypt per-project secrets stored in `project_git_configs` (today: Azure Repos and GitHub PATs), the per-org AI Agent provider API keys in `ai_agent_org_configs` (Anthropic, OpenAI, Google Gemini, OpenRouter, Azure OpenAI, Groq, DeepSeek, Mistral — all eight providers share the same encryption scheme), **and** the AI Key library rows in `ai_agent_keys` (multi-key per org with one default + per-project override via `ai_agent_project_configs.ai_key_id`; the legacy single-key columns on `ai_agent_org_configs` are migrated into this table at boot and kept as deprecated read-only columns). Any reasonably-long random string; the server hashes it with SHA-256 to derive an AES-256-GCM key. Required as soon as Settings → Git Repos or Tools → AI Agent is used. Rotating it invalidates every stored PAT and AI provider key.
- `SKIP_PLAYWRIGHT_INSTALL=1`: Bypass Playwright Chromium installation during `pnpm install`.

## Cross-origin policy

- `CORS_ALLOWED_ORIGINS` (optional, comma-separated absolute origins): Browser origins allowed to call this API and to open its WebSockets, e.g. `http://localhost:5173,https://memento.example`. **Usually empty in production**: the SPA is served same-origin from the api-server process, and same-origin requests are always allowed without configuration. The list exists mainly for local development where Vite serves the SPA on a different port. One list governs three things so they cannot drift: the CORS middleware, the CSRF origin guard on state-changing requests, and the WebSocket upgrade guard. An origin that is present and not on the list is **rejected, never reflected**; a request with no `Origin` header at all (curl, CI, bearer-token machine callers) is allowed, since CSRF requires a browser and browsers always send it. The effective policy is logged at boot.
**Session lifetime** is not configurable by env var. The cookie carries a 7-day rolling `maxAge`, and `shared/middlewares/session.ts` additionally enforces a hard 24-hour ceiling from session creation that `rolling: true` cannot extend — without it, a continuously-used (or stolen) cookie never expired. Sessions created before that cap shipped are stamped lazily, so the deploy does not log everyone out at once.

**Rate limiting** is not configurable by env var — the budgets are fixed in `shared/middlewares/rateLimit.ts`: sign-in 10 attempts / 15 min charged per-IP **and** per-username, `POST /auth/guest` 5 / 15 min per IP, and the email-triggering endpoints (`/auth/password-reset`, `/auth/sso/request-access`) 5 / 15 min per IP. Counters are in-process, which is correct while the deployment is single-instance (the recording session is a module-level singleton, so a second machine would already break the product). If this ever scales out, the counters must move to Postgres alongside the session store.

- `TRUST_PROXY_HOPS` (optional, default `1`): How many reverse-proxy hops to trust for `X-Forwarded-*`. `1` is correct behind Fly's edge and is what makes `req.secure` and `req.ip` meaningful — `req.ip` in particular now backs the per-IP rate limiting, so getting it wrong either lumps every caller into one bucket (too low) or lets a client spoof `X-Forwarded-For` to escape the limit (too high, when the process is reachable without the proxy). Set to `0` only if this process is exposed directly with no proxy in front.

- `CSP_ENFORCE` (optional, `1`/`true`/`yes`): Send the Content-Security-Policy as enforcing rather than report-only. Defaults to **report-only** so a subtly-wrong policy cannot break the UI on deploy. Confirm the browser console is clean against the real app, then turn this on. The other security headers (HSTS, `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`, `Cross-Origin-Opener-Policy`) are always enforced and carry no such risk.

## OIDC / SSO

- `OIDC_ISSUER_URL`, `OIDC_REDIRECT_URL`: Required to enable the "Sign in with SSO" path. When unset, the SSO routes return 404 and only local username/password sign-in is available.
- `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET`: The OIDC client credentials issued by your identity provider. SSO is enabled only when all four required values (issuer, redirect, client id, client secret) are present. If some are set but not all, the api-server logs a single warning at boot naming the missing variables.
- `OIDC_ORG_CLAIM` (default `org`), `OIDC_ORG_DISPLAY_NAME_CLAIM` (optional): Names of the IdP claims that carry the user's organization membership(s) and a friendly display name.
- `OIDC_USER_CLAIMS_NAMESPACE` (default `https://your-idp.example.com/claims`), `OIDC_MEMENTO_USER_CLAIM` (default `mementoUser`), `OIDC_MEMENTO_ACCESS_CLAIM` (default `mementoAccess`), `OIDC_MEMENTO_ADMIN_CLAIM` (default `mementoAdmin`): Names of the claim gates checked on every SSO sign-in (task #1). The admin-gate (`mementoAdmin`, case-sensitive, lives **inside** the namespaced object alongside `mementoUser`) gates the god-mode `memento_admin` role — when the IdP asserts the "Memento Admin" role *without* this claim being truthy, the role is silently downgraded to plain `admin` (the user still signs in, just without cross-org visibility). Promoting a user to Memento Admin therefore requires both an IdP role assignment **and** flipping `mementoAdmin: true` on that user's custom claims. The user-gate (`mementoUser`, case-sensitive) lives **inside** the namespaced object — without it, the callback redirects to `/login?sso_error=no_memento_user` and never establishes a session or provisions the user. The org-gate (`mementoAccess`, case-sensitive) lives **inside each `organizations[]` entry** alongside the org's `id`/`name`/`roles` (granted by the IdP's `organizations` scope) — only orgs whose entry carries this claim as truthy contribute to the user's memento membership. When none of the user's orgs grant access the callback redirects to `/login?sso_error=no_memento_access`; the existing zero-orgs case still redirects to `?sso_error=no_org`. `org_id` at the top level is no longer consulted for the gate. Roles (`OIDC_ROLES_CLAIM`, see below) are also read from inside the namespace when present. The defaults are overridable, so point these at your identity provider's own claim names as needed. Memento Admin bypasses the org-gate (god-mode super role). Local username/password sign-ins are unaffected.
- `OIDC_ROLES_CLAIM` (default `roles`): Name of the IdP claim that carries the user's memento role assignments. Recognized values are the four canonical role names — `Memento Admin`, `Admin`, `Limited Admin`, and `User` — matched case- and whitespace-insensitively. **Roles are per-org, not global.** The identity provider emits each user's role(s) inside their `organizations[]` entry (`organizations: [{ id, name, roles: ["Admin"] }, …]`); a top-level `roles` claim is still honored as a fallback when the namespaced/per-org shape isn't present, and (as a security guardrail) an explicit top-level `User` always wins over a stale per-org `Admin` so an IdP-side downgrade can't be defeated by an out-of-date membership claim. Memento stores per-org roles on `user_organizations.role` (one row per org, with the raw IdP role string captured in `user_organizations.idp_role` for auditability) and resolves the caller's *effective* role at request time from the active org via `resolveEffectiveRole`. Precedence: `memento_admin` (god-mode, org-independent) > local `users.role` (pre-org global view) > the per-org membership row for the session's `activeOrgId`; SSO users with no active org or whose active org was revoked by the IdP resolve to `null` and the route guards translate that to a 403 with "Select an active organization to continue." For SSO users `users.role` is reserved exclusively for the `memento_admin` flag; every other SSO user lands at a neutral `limited` baseline on the row and gets their authority from the membership row, so an "Admin in OrgA + Limited Admin in OrgB" user is correctly demoted to Limited Admin while OrgB is active. The per-org role is re-applied on every sign-in, so a role change at the identity provider takes effect on the user's next login without an admin editing the user inside memento. `Memento Admin` is memento's god-mode super role — sees every project across every org (org-scope filter bypassed) and bypasses the per-org resolver. Missing or unrecognized values default to User on the membership row. Seeded local user (development environments only — see `APP_ENVIRONMENT`): `MementoAdminRole` / `Temporary1!`.
- **SSO callback URL**: When you register memento as an OIDC client with your identity provider, set the redirect URI to `<origin>/api/auth/sso/callback` (e.g. `https://your-app.fly.dev/api/auth/sso/callback`). This must match `OIDC_REDIRECT_URL`.
- **Bearer-token auth on `/api/*`**: Once the four SSO env vars above are set, memento additionally accepts an identity-provider-issued OAuth2 access token in `Authorization: Bearer <token>` on any `/api/*` request — no session cookie required. The token is verified against the identity provider's JWKS (issuer + audience pinned to your client id, expiry enforced); on success memento provisions/updates the matching user the same way the SSO callback does. Missing/expired/wrong-audience tokens return `401`. When SSO isn't configured, bearer tokens are ignored and the existing session-cookie behavior is unchanged. Example: `curl -H "Authorization: Bearer $OIDC_ACCESS_TOKEN" https://your-app.fly.dev/api/auth/me`.
- `OIDC_POST_LOGIN_REDIRECT` (default `/`): Where the SSO callback sends the browser after a successful sign-in.
- `OIDC_POST_LOGOUT_REDIRECT_URL` (optional): Absolute URL the IDP returns to after `end_session_endpoint` on logout. When unset, memento derives `<request origin>${OIDC_POST_LOGIN_REDIRECT}logged-out` from the logout request so the user lands on memento's post-logout confirmation page.

## IdP user provisioning

- `IDP_PROVISIONING_ENABLED`: Set to `1`/`true` to enable the "Provision in identity provider" toggle in Settings → Users → Add user. The toggle routes through the server-side `IdpUserProvisioner` port. When `IDP_API_BASE_URL` is set, the real IdP adapter is installed; per-request the adapter resolves the IdP partner API key from the per-org config rows for the calling memento org first, falling back to the deployment-wide `IDP_API_KEY` env var when no per-org row exists. If neither source yields a key, the adapter returns a "IdP API key not configured" 503. If the toggle is on but `IDP_API_BASE_URL` is missing, the api-server logs a single warning at boot.
- `IDP_API_BASE_URL`: Base URL of your identity provider, e.g. `https://your-idp.example.com`. Also used by the Profile → Password tab's `POST /api/auth/password-reset` endpoint, which derives `${IDP_API_BASE_URL}/api/auth/forgot-password` to ask the identity provider to email the signed-in user a reset link. When unset, the route returns `503` with the same "Set IDP_API_BASE_URL (or IDP_FORGOT_PASSWORD_URL) to enable it." wording used by the provisioning stub.
- `IDP_FORGOT_PASSWORD_URL` (optional): Absolute URL of the identity provider's public forgot-password endpoint. Only needed when the password-reset path doesn't live at the default `${IDP_API_BASE_URL}/api/auth/forgot-password` (e.g. a reverse-proxied deployment or an identity provider that exposes the same `POST { email }` contract at a different path). When set, this URL is used verbatim and takes precedence over the derived value; `IDP_API_BASE_URL` is no longer required by the password-reset route in that case. The endpoint is called with no auth headers and a JSON body of `{ email }`; the identity provider's 200 / 404 / 429 / 5xx responses map to memento's 200 / 200 / 429 / 502 respectively.
- `IDP_API_KEY`: **Optional, deployment-wide fallback** IdP partner API key. The primary source of partner keys is **per-org rows** in the IdP config table (encrypted with `PROJECT_SECRETS_KEY`), managed by each org's admins in Admin → Source control → IdP partner keys. The api-server resolves the key per request — first the per-org row for the calling memento org, then this env var when no row exists. memento authenticates as the integration itself by sending `Authorization: Bearer <resolved-key>` on `POST ${IDP_API_BASE_URL}/api/users/provision` (body `{ email, firstName, lastName, organizationId, password, invitationCodeOnly: false }`) and `POST ${IDP_API_BASE_URL}/api/users/{id}/resend-welcome`. There is no per-admin OAuth2 access token forwarded — the identity provider's partner endpoints reject user OAuth2 tokens. Authorization collapses to "the key's org scope must match the `organizationId` we send"; memento layers Admin-only access on the route in front of it, **plus an additional policy gate that the calling admin must have signed in via SSO** (proven by an OIDC access token on the session, or a Bearer-validated token on the request). Local username/password admins (seeded users, dev-login) get a 403 with an "SSO required" message — they can still create local username/password users via the same route (`provisionInIdp=false`) but cannot create or message IdP users. The same SSO gate applies to `POST /users/:id/resend-welcome`. The `organizationId` sent to the identity provider comes from the calling admin's active SSO org (`req.session.activeOrgId`); admins with no active org get a 403 asking them to pick one first. The provision endpoint does **not** accept a `roleId` — the identity provider assigns the org's default role at create time. Memento still stores the role chosen in the Add User dialog on its own users row, so memento-side RBAC works immediately; promoting the IdP-side role to match must be done in the identity provider's admin UI. On successful create/link, memento stamps the new user's `users.provisioned_in_org_id` with the active memento org so resend-welcome later resolves the right per-org key even if the calling admin's active org has changed.
- The same IdP user GUID returned from `/api/users/provision` is later used by `POST /api/users/{id}/resend-welcome` (admin-only) — surfaced in the UI as a "Resend welcome" button next to each IdP-provisioned user. The route reads the target user's `provisioned_in_org_id` (falling back to the caller's active org for legacy users with no recorded provisioning org) and threads it through the key resolver so the right per-org IdP key is used. The adapter maps the identity provider's 429 → HTTP 429 with the IdP's `Retry-After` echoed back, 404 → HTTP 404, anything else → HTTP 502 with the verbatim reason.
- **Per-org IdP API keys API**: admins can list, fetch, store/replace, and clear the per-org IdP partner key through the IdP-config admin endpoints. Each entry reports status only (`{ organizationId, organizationName, hasKey, apiKeyLastFour, updatedAt, updatedByUsername }`). Auth: Memento Admin sees/mutates everything; non-Memento admins only see + mutate orgs where their `user_organizations.role` is `admin` (limited admins are read-only). Full keys are never returned in plaintext — only the last four characters.
